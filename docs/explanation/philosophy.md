# Arshy 产品哲学与 Token 克制主义

本篇文档定义并阐述 Arshy 的核心设计哲学、输出克制准则，以及面向 AI Agent 运行环境的高密度信息决策体系。

---

## 1. 核心设计哲学：语义执行管道

在现有的 AI 工具链生态中，对于命令输出的治理存在两种完全不同的路线：

```
后处理层（如 RTK / Headroom）:
Agent ──> Bash ──> [运行结束] ──> 获取完整冗余日志 ──> 进行压缩过滤/ML过滤 ──> Agent

Arshy 语义执行管道:
Agent ──> Arshy (MCP/Hook) ──> [PTY 实时执行] ──> [6层流水线实时解析] ──> 结构化数据落库 ──> 克制化响应 ──> Agent
```

*   **RTK/Headroom 是“清洁工”：** 它们不干涉命令的运行，只在事后清理和压缩长篇大论的控制台输出，其目标是**追求文本的压缩率**。
*   **Arshy 是“空中交通管制员”：** 我们直接托管命令的运行周期，在执行时完成语义提取。其目标是**提供高密度的精确诊断锚点，将判断的权利全权移交给 Agent 本身**。

---

## 2. Token 克制主义三准则

为了防止 Agent 对话上下文被冗余信息污染（Context Clutter），Arshy 在输出端秉持极致的克制设计，遵循以下三条核心准则：

### 准则一：默认只推送“状态摘要”，禁止全量事件堆积 (Lazy Pull over Push)
无论命令的日志有多长，在 MCP 工具调用接口（如 `arshy_exec`）返回给 Agent 的主线上下文里，**有且仅有一行简明扼要的状态报告**。
*   **编译成功：** `✓ 0 errors, 2.3s` (仅消耗约 5 个 Token)。
*   **编译失败：** `✗ 3 errors, 10.5s (exit 1)` 并仅带上一条**最关键的 Root Cause 错误定位与 Git 改动摘要**。
*   **按需提取：** 如果 Agent 想要获取其余 2 个错误的详细行号与上下文信息，它必须显式调用另一个专门工具 `arshy_query`（即主被动分离的 Pull 模式）。这避免了在 90% 的正常运行场景下，无谓地把几千字节的解析事件堆进主对话中。

### 准则二：不提供 LLM 已知常识，不做无用功 (No World-Knowledge Redundancy)
LLM（如 Sonnet 或 Gemini）已经拥有了海量的编译器文档和错误代码先验知识。
*   **反面教材：** 在解析出 Rust 编译错误 `E0308` 时，在输出端附带“E0308 意味着类型不匹配，例如预期的类型与发现的类型不一致...”。这属于**低价值的垃圾噪音**，因为 LLM 本身就对 `E0308` 的定义倒背如流。
*   **Arshy 做法：** 屏蔽所有通用的离线修复提示，错误详情中仅保留 `message` 本身。

### 准则三：只在 Stateful 层面补充“环境特异性提示” (Environment Heuristics Only)
LLM 脑容量再大，也无法隔空感知运行主机的当前状态。Arshy 仅在发现 **由于本地运行环境配置异常导致的执行失败** 时，才附带一句话修复指南：
*   *环境特异性 Hint 示例：* 
    `"Hint: ESLint failed to load plugin 'react'. It is declared in package.json but missing in node_modules. Run npm install to resolve."`
*   这种提示无法通过静态常识推导，它是由 Arshy 动态扫描本地依赖与 lockfile 变化得出的，能直接帮 Agent 阻断盲目推测的试错链条。

## 3. 人人与人机的清晰边界 (Transparent Hooking)

Arshy 的 Hook 劫持垫片在 `$PATH` 中完全遵循 **人机隔离** 的核心逻辑：

1.  **人类开发场景：** 100% 旁路。只要没有检测到 Agent 特有的环境变量或父进程签名，垫片直接将操作以 `execvp` 无缝移交真实 Shell。终端没有多余的格式化、没有颜色框装饰，速度零衰减。
2.  **Agent 开发场景：** 零配置激活劫持。所有的编译报错和环境诊断都会流经分析层并入库，过滤控制台 90% 的编译器冗余进度条与 Warning 噪声，最终输出完全保持格式化的结构化清洁结果。

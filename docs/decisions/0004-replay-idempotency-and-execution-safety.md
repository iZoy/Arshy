# ADR-0004: 请求重放幂等 + 并发上限执行 + 空闲退出修复

- **状态**:已采纳（2026-08-22）
- **关联决策**:零争议清理（必修项）
- **相关代码**:`src/daemon/exec/`、`src/daemon/store/`、`src/proxy/handlers.rs`

## 背景

三项"配置/实现与声明落差"：

1. **重放非幂等**：代理在连接抖动后整体重放 `tools/call`，若首次请求已到达守护进程、仅响应丢失，`git push`/`rm` 等有副作用命令会被**执行两次**；
2. **`max_concurrent_tasks` 死配置**：配置声明默认 4 但从未执行（无任务并发信号量）；
3. **空闲退出失效**：短命令不落库，`idle_since_secs()` 在无已完成任务时返回 `None`，看门狗当"不空闲"→ 只服务短命令的守护进程永不退出。

## 决策

1. **幂等重放**：`RunTaskParams` 新增 `dedup_key`（代理注入 MCP 请求 id），执行器按 key 缓存结果 120 秒（上限 256 条）；同 key 重放返回原结果，正常重复调用（每次新 id）不受影响；
2. **并发上限落地**：结构化路径用 tokio 信号量执行 `max_concurrent_tasks`，超限返回可重试的 `RATE_LIMITED` 错误；短路径不受限（已有速率限制器兜底）；
3. **空闲修复**：Store 用 `AtomicI64` 记录最近活动时间（每条命令 + 长任务完成时刷新），`idle_since_secs()` 仅在任务运行中返回 `None`，否则返回距最近活动的时间。

## 理由

1. 重复执行破坏性命令是唯一"可能造成真实损失"的路径，优先修；
2. 死配置二选一时选择"实现"，因为安全模型文档明确把并发上限列为资源防护；
3. 空闲修复让"用完即走"承诺对短命令场景也成立。

## 后果

- 正面：三类真实风险消除；新增幂等/并发/空闲测试；
- 负面：幂等缓存占用有限内存（256 条 × 120s，可忽略）；并发拒绝语义需要 agent 感知重试；
- 风险：120s TTL 之外的重放仍会重复执行（窗口远超代理重连耗时，可接受）。
